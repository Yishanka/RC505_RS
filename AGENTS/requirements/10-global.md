# Global Requirements

## 1. 目标

所有开发任务都应以“完整、可继续维护的工程交付”为目标，而不是只改到局部可用。

默认要求：

1. 正确识别任务类型
2. 阅读相关代码与已有历史文档
3. 评估影响范围
4. 在合适层级完成改动
5. 给出验证方法
6. 写入对应文档目录

---

## 2. 必读上下文

在读取本文件后，应根据任务继续阅读：

1. 相关源码
2. 对应历史文档目录
3. 与该模块直接相关的配置、DSP、Engine、Project 代码

建议优先检查的项目结构：

1. `src/ui/`
2. `src/config/`
3. `src/dsp/`
4. `src/engine/`
5. `src/project.rs`

---

## 3. 共同行为规则

### 3.1 先分类，再开发

任务必须先归类为：

1. 功能开发
2. 逻辑问题修改 / 功能普通修改 / 功能删除
3. 架构调整 / 代码风格 / 非功能性重构

### 3.2 默认不要修改 `AGENTS/PLAN.md`

除非提示词明确要求，否则：

1. 不新增计划项
2. 不顺手改完成状态
3. 不把本次实现自动回写到 `PLAN.md`

### 3.3 优先沿用现有结构

默认沿用当前目录与模块边界实现。

只有在现有结构无法支撑需求时，才进行结构调整，并且要满足重构类规范。

### 3.4 不要无文档交付

只要发生改动，就必须写文档。

文档不是流水账，必须让后续模型能快速接手。

### 3.5 音频项目的验证要求

音频类任务可以不强制补自动化测试，但必须提供：

1. 可复现的手工操作步骤
2. 预期结果
3. 若无法完整验证，说明阻塞原因

---

## 4. 默认执行流程

除非用户明确要求只做分析，否则按以下流程执行：

1. 读取入口与专项要求文档
2. 阅读相关代码和历史文档
3. 明确影响范围
4. 实施修改
5. 做必要验证
6. 写入对应文档
7. 汇报分类、范围、验证、文档和风险

---

## 5. 最终汇报最低要求

最终说明至少包含：

1. 本次任务属于哪一类
2. 改动覆盖了哪些层或模块
3. 文档写到了哪个目录 / 文件
4. 做了哪些验证
5. 还有哪些风险、限制或未完成项
